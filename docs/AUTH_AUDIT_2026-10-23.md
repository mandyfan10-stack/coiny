# Проверка входа — 23 октября 2026

База проверки: версия 1.20.84. Продолжение проверки — 24 октября. Клиентские изменения подготовлены для релиза 1.20.86; миграций базы нет.

## Согласованные исправления

1. **Вход по username после привязки email.** После отказа двух прежних внутренних адресов клиент использует существующую серверную `username-login`. Адрес аккаунта остаётся на сервере; клиент получает сеанс только после проверки пароля. Прямой вход по email, старые аккаунты и обработка ограничения попыток сохранены.
2. **Восстановление пароля.** Адрес возврата сохраняет путь `/coiny/`. Отдельный экран проверяет ссылку, принимает новый пароль и завершает временный сеанс. Токены удаляются из адресной строки до сетевых запросов. Запись пароля привязана к отдельному клиенту с проверенным токеном, поэтому замена основного аккаунта не меняет цель запроса. Ошибочная ссылка не удаляет сохранённый вход другого аккаунта.
3. **Согласованность сеанса.** Поздняя первоначальная загрузка, старый профиль и завершение прежнего выхода не заменяют новый вход. При смене аккаунта старая личность скрывается сразу. Ошибка загрузки профиля показывает повтор и выход; ошибка фонового обновления сохраняет уже открытый аккаунт.
4. **Запоздалое обновление email.** Ответ прежнего сеанса игнорируется после выхода или смены аккаунта, в том числе при повторном входе тем же пользователем. Настройки не показывают успех отменённой операции.
5. **«Запомнить меня».** Постоянный вход хранится в `localStorage`, временный — в `sessionStorage`. Перезагрузка вкладки сохраняет временный вход; восстановление только постоянного состояния в новом браузерном контексте его не возвращает. Обновление токенов сохраняет выбранный режим. Старые постоянные входы продолжают работать. Межвкладочные события сверяются с фактическим токеном вкладки.
6. **Доступ приложений к входу по username.** Серверная функция разрешает точные источники `app://coiny` (Windows) и `https://localhost` (Android). Проверка пароля, квоты и запрет посторонних источников сохранены.

## Серверная часть

За основу взята работающая `username-login` v3. Перед применением побайтно проверено, что изменение функции состоит только из добавления двух разрешённых источников приложений. По отдельному согласованию пользователя на сервер применена v4; её исходник совпадает с локальным. Служебные функции поиска аккаунта и квот недоступны ролям `anon` и `authenticated`; права не менялись.

После применения на рабочем сервере проверены OPTIONS-запросы без логинов и паролей: сайт, Windows и Android получают 204 с точным разрешённым источником; `https://example.invalid` получает 403 без разрешения CORS. Проверки парольной ветки выполняются на искусственных данных через границу SDK. Полный вход через установленный APK или EXE с настоящими учётными данными не выполнялся.

С активным publishable key, побайтно подтверждённым в опубликованном клиентском файле, для всех трёх источников проверен также POST с некорректным JSON: сервер доходит до проверки тела и возвращает ожидаемые 400. Эти запросы завершаются до обращения к квотам или аккаунтам. Дополнительная проверка старого anon key вернула 401; текущая опубликованная сборка использует проверенный publishable key.

Исправлена отдельная ошибка настроек Auth: рабочие адреса возврата Coiny отклонялись, запасной Site URL был `localhost:3000`. После согласования и входа пользователя в панель Supabase настройки сохранены через URL Configuration. Аккаунты и данные базы не изменялись.

Сохранённые значения рабочего проекта:

- Site URL: `https://mandyfan10-stack.github.io/coiny/`.
- Redirect URLs: `https://mandyfan10-stack.github.io/coiny/` и `https://mandyfan10-stack.github.io/coiny/?auth=recovery`. Ранее список был пуст.
- Проверка после сохранения: запрос с недействительным тестовым токеном возвращает 303 на `/coiny/?auth=recovery`. Посторонний `example.invalid` отклоняется и возвращает 303 на канонический `/coiny/` без recovery-маркера. Письма не отправлялись.

В локальную конфигурацию добавлены точные адреса восстановления для существующих портов разработки. Локальный Site URL сохранён для локального запуска.

## Исправление стенда перед повторным выпуском

Попытка выпуска 1.20.85 остановилась на проверке группового аудио, без публикации сайта или установщиков. В стенде несколько CallProvider работают в одном документе, а очистка проигрывателей рассчитана на отдельное окно приложения. Отказ третьего участника удалял проигрыватели остальных: оба WebRTC-соединения оставались подключёнными, пакеты шли, но декодирование звука останавливалось. Добавление отдельного выхода для настоящего принятого трека восстанавливало измерение аудио без изменения соединения.

По согласованию пользователя исправлен только групповой стенд: каждому настоящему RTCPeerConnection предоставлен независимый аудиовыход, который освобождается при завершении трека или закрытии соединения. Он не генерирует звук и не подменяет getStats; исходные проверки живых треков, роста RTP и энергии аудио сохранены. Ранее падавший сценарий прошёл 20 раз подряд без retries. Неудачный тег 1.20.85 сохранён; следующий выпуск — 1.20.86.

Окончательный групповой вариант прошёл весь набор транспорта: 136/136 в Chromium/WebKit на компьютере и телефоне, без повторных попыток. В первом расширенном варианте один личный сценарий WebKit потребовал дополнительной проверки; окончательная правка ограничена групповым стендом, и тот же личный сценарий прошёл в полном прогоне.
